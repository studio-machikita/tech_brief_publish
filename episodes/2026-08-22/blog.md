## 🤖 Slackで使える新しいGitHub Copilot体験
`AI` `DevOps`

<details>
<summary>📄 原題: The new GitHub Copilot experience in Slack</summary>
</details>

> **一言で**: GitHub CopilotがSlackで公開プレビュー開始

- SlackのGitHub連携でCopilotのエージェント機能が使えるように
- GitHub Copilot CLIとCopilotアプリの機能をSlack内で利用できる
- 現在は公開プレビュー(パブリックプレビュー)段階
- Slack上で「@GitHub」と呼びかけて作業を依頼できる

💡 **なぜ重要か**
開発者は普段からSlackでチームとやり取りしており、コード作業のたびにツールを切り替える手間がありました。GitHub CopilotをSlackに統合することで、コミュニケーションの場から離れずに開発タスクを進められるようになります。エージェント機能をチャットツールに組み込む流れは、AIアシスタントが単独のツールから日常業務に溶け込む存在へ変わりつつあることを示しています。 チャットツールとAI開発支援の融合が進むと見られています。SlackやTeamsのようなコラボレーションツールが、開発ワークフローの中心になる可能性があります。他のAIベンダーも同様の統合を加速させ、ツール間の垣根がさらに低くなっていくと考えられます。

🎯 **今日のアクション**
エンジニアはまず公開プレビューを試し、日常のSlackワークフローにどう組み込めるか検証すべきです。チームリーダーは、Copilotのエージェント機能がコードレビューやタスク管理にどう影響するか評価し、導入ガイドラインを整備しておくとよいでしょう。

🔗 [原文を読む](https://github.blog/changelog/2026-08-21-the-new-github-copilot-experience-in-slack)

## 💼 知られざる新興予測市場、その戦略的な正体
`Business` `Startup` `Web`

<details>
<summary>📄 原題: The Hot New Prediction Exchange You’ve Never Heard of—by Design</summary>
</details>

> **一言で**: 黒子役の予測市場取引所Rothera、業界の裏方に台頭

- Rotheraは消費者向けアプリを持たず、証券会社などに取引所機能だけを提供
- Robinhood と Susquehanna が出資、両社は今夏から取引をRotheraに回している
- MIAXから79億円規模でライセンス済み取引所を買収し、規制対応を短縮
- 6月の取引開始からすでに出来高で上位5位の取引所に浮上
- 最大手Kalshiやポリマーケットとは競合せず、証券会社の裏側を支える立場を狙う

💡 **なぜ重要か**
予測市場はKalshiとPolymarketが消費者向けアプリと取引所を両方運営し急成長中です。Rotheraはその裏側、つまり証券会社や金融機関が使う「取引所インフラ」だけに特化する戦略を取っています。自社で顧客を抱えず、証券会社の注文を仲介する立場に徹することで、既存プレイヤーと直接競合せずに市場拡大の恩恵を受けようとしています。 予測市場が個人向けだけでなく機関投資家向けにも広がる中、取引所とブローカーの役割分担が伝統的な金融市場のように進む可能性があります。Rotheraのような裏方インフラが増えれば、複数の取引所を使い分ける動きが一般化し、業界の競争構造がより複層的になりそうです。

🎯 **今日のアクション**
予測市場向けサービスを検討するエンジニアやプロダクトリーダーは、自社でアプリと取引所を両方持つべきか、Rotheraのような外部インフラに接続すべきかを早めに見極める必要があります。24時間365日対応の取引システムや規制対応コストも考慮点になります。

🔗 [原文を読む](https://www.theinformation.com/articles/hot-new-prediction-exchange-never-heard-design)

## 🤖 claude のメモリを棚卸しする
`AI` `DevOps`

> **一言で**: Claudeのメモリ機能を改めて調べて棚卸しした話

- Xの投稿がきっかけでClaudeのメモリ機能を見直すことに
- 公式ドキュメントを読んで仕組みを改めて確認
- プロジェクトごとに~/.claude/projects/配下へ保存される仕様
- 設定次第で挙動が変わる部分もあると判明

💡 **なぜ重要か**
Claudeのメモリ機能は「よしなにやってくれる」ものと捉えられがちで、仕組みを意識せずに使っているユーザーが多いと見られています。実際の保存場所や設定を理解しないまま使い続けると、意図しない情報の蓄積や管理不足につながる可能性があります。 AIアシスタントのメモリ機能はプロジェクト単位の情報管理に直結するため、仕組みへの理解不足は開発チーム全体の情報管理リスクになり得ます。今後こうした機能の透明性や設定の分かりやすさが、ツール選定の重要な基準になっていくと考えられます。

🎯 **今日のアクション**
自分が使っているAIツールのメモリ機能について、公式ドキュメントを一度読み、保存場所や設定項目を確認しておくとよいでしょう。

🔗 [原文を読む](https://zenn.dev/cureapp/articles/c1e963064d05fd)

## 🤖 機械学習ベースのヘリコプター重量推定器の機上実装に向けて
`AI` `Hardware`

<details>
<summary>📄 原題: Towards On-Board Implementation of ML-Based Helicopter Weight Estimator</summary>
</details>

> **一言で**: Airbusがヘリの重量をAIで推定、機体搭載を目指す研究

- Airbusの実運航機データを使い、離陸時の重量を推定するAIモデルを開発
- EASAの機械学習向け指針とEurocae ED-324に沿った保証プロセスを整備
- 機械学習の要件定義とモデル仕様書を整理し、機体搭載への準備を提示

💡 **なぜ重要か**
航空機へのAI搭載には安全性の証明が不可欠で、規制当局の指針への準拠が重要な課題です。 航空分野でのAI活用に向けた認証手法が確立すれば、他の安全重視産業にも応用が広がりそうです。

🎯 **今日のアクション**
AIを組み込む機器開発者は、対応する規制指針を早期に確認し設計に反映すべきです。

🔗 [原文を読む](https://arxiv.org/abs/2608.19210)

## 🤖 エージェント型データ運用プラットフォーム(ADOP):データエンジニアリングを数時間で実現
`AI` `Data` `Cloud`

<details>
<summary>📄 原題: Agentic Data Operations Platform (ADOP): Data engineering into hours</summary>
</details>

> **一言で**: AIエージェントでデータ基盤構築を週単位から時間単位に短縮

- Amazon Bedrock上のリファレンス構成「ADOP」を発表
- 専門AIエージェントがBronze・Silver・Goldの一連のデータパイプラインを自動化
- 新しいデータソースの取り込みが数週間から数時間に短縮
- ガバナンスとコンプライアンス管理は自動化後も維持される設計

💡 **なぜ重要か**
データ基盤の構築は、新しいデータソースを追加するたびに設計・変換・検証といった作業が発生し、従来は多くの時間と人手を必要としていました。AIエージェントに専門的な役割を分担させることで、この一連の工程を自動化しようという発想がADOPの背景にあります。 データエンジニアリングの自動化が進むと、企業はデータ活用のスピードを大きく上げられます。一方で、AIエージェントが担う処理の透明性やガバナンス体制の設計が、今後さらに重要な論点になると見られています。

🎯 **今日のアクション**
データ基盤を持つ企業は、自社のパイプライン構築工程のどこがAIエージェントで自動化できるか、まず棚卸しから始めるとよいでしょう。ガバナンス要件を明確にした上で段階的に導入するのが安全です。

🔗 [原文を読む](https://aws.amazon.com/blogs/machine-learning/agentic-data-operations-platform-adop-data-engineering-into-hours/)
